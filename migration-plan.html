Catálogo a Cloudflare R2 + Convex DB

Reemplazar public/songs.json, metadata.json y los archivos de audio estáticos.

Por qué primero

Esta etapa desbloquea todo lo demás. Una vez que los MP3s viven en R2 y la metadata en Convex, la Etapa 2 (Modal) solo necesita saber a dónde subir los stems; y la Etapa 3 (auth) solo agrega tablas nuevas al schema existente. El player sigue funcionando igual — solo cambia la URL del fetch.

Schema Convex

// convex/schema.ts songs: defineTable({ title: v.string(), artist: v.string(), bpm: v.optional(v.number()), slug: v.string(), // "blackbird" — preserva las URLs /song/blackbird isPublic: v.boolean(), // true = catálogo público ownerId: v.optional(v.string()), // null ahora; userId en Etapa 3 chordsFile: v.optional(v.string()), // R2 path: "songs/blackbird/acordes.pdf" tracks: v.array(v.object({ id: v.string(), // "voz", "instrumental" label: v.string(), // "Voz", "Instrumental" file: v.string(), // R2 path: "songs/blackbird/Voz.mp3" defaultVolume: v.number(), })), markers: v.array(v.object({ time: v.number(), label: v.string(), trackIndex: v.optional(v.number()), })), regions: v.array(v.object({ id: v.string(), label: v.string(), start: v.number(), end: v.number(), color: v.optional(v.string()), trackIndex: v.optional(v.number()), })), }) .index("by_slug", ["slug"]) .index("by_public", ["isPublic"]) .index("by_owner", ["ownerId"]) .index("by_artist", ["artist"])

Nota sobre tracks[].file: se guarda el path relativo en R2 ("songs/blackbird/Voz.mp3"), no la URL completa. La URL se construye igual que hoy con rawUrl(). Si la URL pública del bucket cambia, solo hay que cambiar la variable de entorno, no migrar los datos.

Pasos de implementación

  1. Instalar Convex: pnpm add convex → npx convex dev (genera convex/_generated/ y convex.json). Agregar ConvexClientProvider en app/layout.tsx.

  2. Crear bucket R2 en Cloudflare: habilitar acceso público, configurar CORS (AllowedOrigins: tu dominio de Vercel, AllowedMethods: ["GET"]).

  3. Generar API token R2 con permisos de escritura. Agregar variables de entorno: NEXT_PUBLIC_R2_URL, R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET_NAME.

  4. Crear scripts/migrate-to-convex.ts: lee public/songs.json, por cada canción lee metadata.json, sube los MP3s/PDFs a R2 manteniendo el path songs/{id}/Voz.mp3, e inserta el documento en Convex con isPublic: true, ownerId: null.

  5. Correr el script de migración una sola vez: npx tsx scripts/migrate-to-convex.ts. Verificar en el Convex dashboard y en la URL pública de R2.

  6. Actualizar lib/songs.ts: rawUrl(path) devuelve ${NEXT_PUBLIC_R2_URL}/${path} si el env var existe; si no, /${path} como hoy (para desarrollo local sin R2).

  7. Actualizar app/page.tsx para usar fetchQuery(api.songs.listPublic) en lugar de readJsonFromPublic('songs.json').

  8. Actualizar app/song/[id]/page.tsx para usar fetchQuery(api.songs.getBySlug, { slug: id }).

  9. Eliminar lib/songs.server.ts (ya no hay filesystem reads de metadata).

  10. Verificar que el player carga y reproduce audio desde R2. Una vez confirmado, eliminar los binarios de audio del repo (public/songs/*/Voz.mp3, etc.).

⚑ Caveats de la Etapa 1
  • CORS en R2: sin CORS configurado correctamente, el browser no puede hacer fetch() al bucket. El Web Audio API necesita recibir el ArrayBuffer — si hay error de CORS, el audio simplemente no carga y el error es confuso. Verificar con DevTools antes de eliminar los archivos de public/.
  • Content-Type de los MP3s: R2 puede servir archivos con Content-Type: application/octet-stream si no se especifica al subirlos. Asegurarse de pasar ContentType: 'audio/mpeg' al subir con PutObjectCommand, o el browser puede no decodificarlos correctamente.
  • URLs de Convex vs. generadas: los documentos de Convex usan IDs internos (Id<"songs">), no slugs. El campo slug es el que se usa para las URLs del router (/song/blackbird). El índice by_slug debe ser único — agregar una validación en la mutation create.
  • No eliminar public/songs/ hasta verificar: correr el script de migración, confirmar que las 15 canciones están en Convex y los MP3s accesibles en R2, y recién después eliminar los binarios del repo. El historial de git seguirá teniendo los binarios — usar git filter-repo después si importa el tamaño del repo.
  • ISR / cache de Next.js: actualmente app/page.tsx tiene revalidate: 3600. Con Convex las queries son reactivas por defecto en el cliente — decidir si la home es RSC (con fetchQuery en servidor, cache manual) o Client Component (auto-reactivo). Para empezar, RSC con fetchQuery es más simple.
  • Desarrollo local sin R2: el rawUrl() con fallback a / permite seguir usando los archivos de public/ en local si NEXT_PUBLIC_R2_URL no está seteado. Útil mientras se implementa la migración.

Verificación

  • URL pública de R2: https://pub-xxx.r2.dev/songs/blackbird/Voz.mp3 devuelve 200 con Content-Type: audio/mpeg
  • La home lista las 15 canciones cargando desde Convex
  • /song/blackbird carga metadata desde Convex y audio desde R2
  • WaveSurfer renderiza la waveform; el player reproduce correctamente
  • Markers y regions del usuario siguen persistiendo en localStorage

Worker Demucs en Modal

Reemplazar el subprocess de Python local por una función Modal con GPU.

Por qué Modal

Demucs necesita GPU para ser práctico (~10 s con GPU vs. 5-10 min en CPU). Modal permite definir el ambiente de Python con Demucs, yt-dlp y ffmpeg como imagen Docker, y exponer la función como endpoint HTTP. No requiere mantener infraestructura — solo se paga cuando corre. El free tier incluye $30 de créditos que alcanzan para cientos de canciones.

Arquitectura del procesamiento

// Flujo actual (Python local):
browser → POST /api/studio → subprocess Python → escribe public/songs/{id}/ → actualiza songs.json

// Flujo nuevo (Modal + R2 + Convex):
browser → POST /api/studio
  → si hay MP3: subirlo a R2 como temp/{uuid}.mp3
  → llamar endpoint Modal con { audioUrl | youtubeUrl, songId, title, artist, bpm }
  Modal:
    → descarga audio (de R2 temp o YouTube)
    → corre Demucs --two-stems=vocals --mp3
    → sube Voz.mp3 + Instrumental.mp3 a R2: songs/{songId}/
    → (opcional) sube acordes.pdf
    → devuelve { ok: true, songId }
  /api/studio:
    → llama fetchMutation(api.songs.create, { slug, title, artist, tracks, ... })
    → revalida la home
    → responde al browser

Timeout de Vercel — el problema más importante

Las funciones serverless de Vercel tienen límite de 60 s (free tier) o 300 s (Pro). Demucs puede tardar 5-15 minutos en CPU o ~30-60 s en GPU. Hay dos estrategias: 

// Opción A — Polling (recomendado para free tier Vercel)
POST /api/studio → retorna { jobId }  // inmediato, menos de 5 s
Modal procesa en background
Cliente hace polling a GET /api/studio/status?jobId=xxx cada 5 s
Modal escribe songs/{songId}/_status.json en R2 cuando termina
// el cliente lee el status directamente desde R2

// Opción B — SSE mantenido (requiere Vercel Pro o edge functions)
Modal con StreamingResponse emite logs → /api/studio los reenvía como SSE
// Igual al flujo actual con Python, pero con el worker en la nube
⚑ Caveats de la Etapa 2
  • Cold start de Modal: la primera invocación puede tardar 30-60 s mientras baja la imagen Docker con Demucs (~3 GB). Las siguientes son mucho más rápidas. Comunicarlo al usuario en la UI del Studio.
  • Subir MP3 del usuario antes de llamar a Modal: el browser sube a /api/studio, pero Vercel no puede pasar ese buffer directamente a Modal si la función serverless no tiene estado persistente. La solución es subir el MP3 a R2 en una ruta temporal (tmp/{uuid}.mp3) y pasarle la URL a Modal. Limpiar esa ruta temporal una vez que Modal termina.
  • Credenciales de R2 en Modal: usar modal.Secret.from_name("r2-credentials") para no hardcodear las claves. No pasarlas en el body del request.
  • Model de Demucs: htdemucs_2stems es el mismo que usa el script Python actual. Si se cambia el modelo, los paths de salida de Demucs cambian.
  • yt-dlp en la nube: YouTube puede bloquear peticiones desde IPs de data centers. Puede ser necesario configurar un proxy o usar cookies autenticadas. Testear antes de dar por buena la feature.
  • Sin SSE en Vercel free: con la Opción A de polling, el cliente pierde el log en tiempo real de las fases (downloading, separating, uploading). Mostrar un spinner genérico con el status del job es suficiente para empezar.

Autenticación y listas por usuario

Convex Auth (o Clerk) + tabla userLibrary para listas personales.

Modelo de datos — qué se agrega

El schema de la Etapa 1 ya tiene isPublic y ownerId preparados para esta etapa. Solo se agrega la tabla userLibrary y se conecta la autenticación.

// convex/schema.ts — se agrega esto en Etapa 3 userLibrary: defineTable({ userId: v.string(), // Convex Auth identity subject songId: v.id("songs"), addedAt: v.number(), // Date.now() }) .index("by_user", ["userId"]) .index("by_user_and_song", ["userId", "songId"])

Flujos de usuario

// Sin login — igual que hoy
Home → muestra catálogo público (listPublic)
Player → carga metadata desde Convex, audio desde R2
Markers/Regions → localStorage

// Con login
Home → muestra "Catálogo" + "Mi lista" (canciones guardadas + privadas)
Player → igual que sin login
"Guardar canción" → addToLibrary(userId, songId)
Studio → canción subida se crea con ownerId=userId, isPublic=false
"Publicar al catálogo" → (acción futura, solo admin o con moderación)

Opciones de autenticación

Convex Auth (recomendado): auth nativa de Convex, sin servicio externo. Soporta Google OAuth, GitHub, magic links. Integra directamente con las queries — en cada mutation se puede obtener ctx.auth.getUserIdentity(). Sin costo adicional.

Clerk: mejor UX de auth (componentes pre-construidos, más providers). Tiene integración oficial con Convex via JWT. Agrega un servicio externo pero el free tier es generoso (10K usuarios/mes).

⚑ Caveats de la Etapa 3
  • Rutas públicas vs. protegidas: el catálogo público no debe requerir login para acceder — verificar que listPublic y getBySlug (para canciones públicas) no tengan guard de auth.
  • Canciones privadas y URLs de R2: si un usuario sube una canción privada y el bucket de R2 es público, cualquiera con la URL puede acceder al MP3. Opciones: (a) bucket privado con URLs firmadas de corta duración, (b) aceptarlo como limitación inicial dado que las URLs no son predecibles.
  • Migración de localStorage a Convex para el estado del player: si en el futuro se decide sincronizar markers/regions entre dispositivos, la tabla userSongState ya está diseñada para eso. No es necesario en esta etapa.
  • Slugs de canciones privadas: si dos usuarios suben la misma canción, puede haber colisión de slugs. Agregar el userId como prefijo en el slug de canciones privadas: {userId}-{slug}.
  • El Studio en producción: actualmente el Studio tiene un guard de desarrollo (process.env.NODE_ENV === 'development'). Con auth, el guard cambia a "solo usuarios autenticados" o "solo admin". Definir qué usuarios pueden agregar al catálogo público.
